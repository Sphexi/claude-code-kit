# Architecture

claude-code-kit has authored and vendored sources, a generator, and three consumers that all read the generator's output.

## Flow

```
shared/*.md ──inline_shared.py──▶ claude/{agents,output-styles,global-CLAUDE.md}
upstream clones ──vendor_sync.py──▶ claude/vendor/ + claude/plugins.manifest.json
claude/ + shared/ + build/kit.json ──build_plugins.py──▶ plugins/, .claude-plugin/marketplace.json,
                                                          THIRD_PARTY_NOTICES.md, docs/plugins.md
plugins/ ──marketplace──▶ users' plugin cache
plugins/ + claude/global-CLAUDE.md + claude/settings.* ──tools/payload.py──▶ deploy, refresh
plugins/ + cowork/ ──build_plugins.py --zip──▶ dist/*.zip
```

## Directories

| Path | Role |
|---|---|
| `claude/` | Authored source: `agents/`, `output-styles/`, `skills/`, `global-CLAUDE.md`, the settings files |
| `claude/vendor/<plugin>/` | Third-party plugins, one directory per upstream plugin. Written only by `tools/vendor_sync.py` |
| `claude/plugins.manifest.json` | Provenance and license data for the vendored plugins. Generated by `tools/vendor_sync.py` |
| `shared/` | Canonical prose blocks inlined into the payload |
| `cowork/` | Overlay added to the core Cowork zip only |
| `build/` | `kit.json`, `bundles.py`, `inline_shared.py`, `build_plugins.py` and the templates |
| `plugins/sphexi-<name>/` | Generated marketplace plugin roots. Deploy reads these too |
| `.claude-plugin/marketplace.json` | Generated marketplace listing |
| `tools/` | The deploy and refresh engine, the layout table, the state file, `vendor_sync.py` |
| `scripts/`, `deploy.*`, `refresh.*` | Wrappers that find Python and run the engine. No logic |
| `tests/python/` | The pytest suite |

`claude/global-CLAUDE.md` is not named `CLAUDE.md` so that Claude Code does not load it as a nested memory file whenever a session touches `claude/`.

## Three single-source rules

Each kind of fact lives in exactly one place, and everything else is derived.

**Shared prose.** The terseness rules and code standards live in `shared/`. `build/inline_shared.py` copies them into every file that carries a marker pair. Nothing outside `shared/` is edited by hand between those markers.

**Layout.** `tools/payload.py` is the only table that maps a repository path to a live path. Deploy, refresh and the smoke test all call it, so a deployment installs exactly the files the marketplace serves, and refresh compares exactly those files.

**Identity and version.** `build/kit.json` holds the marketplace name, owner, repository, license, zip prefix, the external marketplace entries and the version. It feeds every generated `plugin.json`, `marketplace.json`, README and zip name.

## Bundles

`build/bundles.py` assigns every vendored plugin to exactly one marketplace plugin, or to `EXTRAS`. A bundle merges its members' agents, commands and skills into one directory, with each member's `LICENSE` and `UPSTREAM.md` under `notices/<member>/`. The build fails on an unassigned plugin, a name collision inside a bundle, or an agent reference that resolves nowhere.

`sphexi-core` is composed differently: its agents, skills and output styles come from `claude/`, plus the vendored `skill-creator`, plus a generated `SessionStart` hook. The hook's payload is the code standards, split at `##` headings into files of at most 9,500 characters, one hook command per file. A single section above that size fails the build.

A marketplace entry's name must equal its generated `plugin.json` name. Entries set no `version`; the pinned `plugin.json` version applies. Dependencies are declared on the entry.

## Why `plugins/` is committed

A marketplace entry with a relative source resolves only against files present in the cloned repository at the ref users track. `/plugin marketplace add sphexi/claude-code-kit` tracks the default branch, so the generated trees must be on that branch. Generating them at release time would need a separate branch or archive sources, and would change the add command.

The cost is that vendored content is stored twice, once per upstream plugin under `claude/vendor/` and once per bundle under `plugins/`. Diffs under `plugins/` are marked `linguist-generated`, which collapses them in GitHub's diff view.

Drift is prevented by comparison: `python build/build_plugins.py --check` regenerates into a temporary directory and compares byte for byte, CI runs it, the release workflow runs it again, and a test runs the same comparison against the real repository. `.gitattributes` forces LF line endings so that a Windows checkout stays byte-identical.

## Deploy and refresh

Deploy classifies each target against the live file and the state file and acts only on files the kit owns; see [deploy.md](deploy.md). Settings are composed from the base file and an OS overlay, then merged into the live file with every addition recorded; see [settings.md](settings.md).

Deploy installs `sphexi-core`'s agents, skills and output styles as user-level files and every other plugin as a directory under `skills/`, which Claude Code loads as a `skills-dir` plugin. Because the manifest names match the marketplace plugins, a marketplace copy takes precedence over a deployed copy, and the deployed copy shows as `Not loaded`.

The state file, `claude-code-kit-state.json`, records every path and settings entry the kit wrote with hashes. Refresh and uninstall use it to separate repository changes from user edits.

## Cowork

The Cowork zips are built from `plugins/`. The core zip adds the overlay in `cowork/`; see [cowork.md](cowork.md).

## Platforms

All behaviour is in Python 3.12 or newer, using only the standard library. The Bash wrappers run on Bash 3.2, the version macOS ships. The PowerShell wrappers target Windows PowerShell 5.1 and contain only ASCII. Names that decide collisions are compared case-folded, because macOS and Windows filesystems are case-insensitive by default.
